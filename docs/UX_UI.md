## 0. PWA не зависит от фреймворка

Коротко: **да, не зависит.** PWA — это три вещи, и ни одна не про Next:

| Что нужно | Где лежит | Зависит от Next? |
|---|---|---|
| `manifest.webmanifest` | `public/` | нет |
| Service worker | `public/sw.js` | нет |
| HTTPS (или localhost) | хостинг | нет |

### Service worker написан руками, без библиотеки

Сначала был подключён `@serwist/next` — его рекомендует документация
Next. Потом он был убран. Разбор, почему.

**Что умеет Serwist и что из этого нужно:**

| Умеет | Нужно? |
|---|---|
| Манифест прекэша с хешами ассетов | ❌ нет, см. ниже |
| Стратегии кэширования Workbox | ❌ нужны две, обе в 5 строк |
| Автоматическая регистрация SW | ❌ 8 строк |
| Версионирование кэша | ⚠️ да, но это 3 строки |

**Ключевое наблюдение.** Файлы в `/_next/static/` содержат хеш в имени,
то есть **неизменяемы**. Для них достаточно `cache-first` с наполнением
на лету — манифест прекэша не нужен. А манифест — единственное, ради
чего плагин лезет в сборку.

Остальные URL стабильны и известны заранее: `/`, `/lesson/`,
`/progress/`, шесть JSON контента. Перечисляются руками.

**Чего Serwist стоил:**

```
+27 пакетов в зависимостях
сборка слезала с Turbopack на webpack (next build --webpack)
три грабли, каждая давала зелёную сборку и мёртвый офлайн
впереди миграция на @serwist/turbopack после перехода на бэкенд
```

**Что осталось вместо него:**

```
apps/web/public/sw.js                 ~90 строк, читаемых
apps/web/app/_providers/ServiceWorker.tsx   8 строк регистрации
scripts/stamp-sw.mjs                  30 строк: подставить версию
```

Сборка вернулась на Turbopack, `next build` без флагов.

### Три стратегии, и почему именно такие

```js
// 1. Навигация — network-first
//    Онлайн всегда свежая страница, офлайн из кэша, иначе /offline/
if (request.mode === 'navigate') …

// 2. /_next/static/* — cache-first
//    Имя содержит хеш → файл неизменяем → манифест не нужен
if (url.pathname.startsWith('/_next/static/')) …

// 3. /content/* — stale-while-revalidate
//    Пакет в прекэше, обновление приезжает фоном
if (url.pathname.startsWith('/content/')) …
```

Почему навигация **network-first**, а не cache-first: при
`output: 'export'` HTML ссылается на хешированные чанки. Отдавать
закэшированный HTML онлайн — значит рисковать ссылками на чанки,
которых после деплоя уже нет.

### Версия кэша

Браузер переустанавливает worker, только если изменился его контент.
`scripts/stamp-sw.mjs` подставляет `VERCEL_GIT_COMMIT_SHA` (или
timestamp локально) в `out/sw.js` после сборки. В `public/sw.js`
остаются плейсхолдеры — репозиторий не грязнится каждой сборкой.

### Что ещё выяснилось про встроенное в Next

| | |
|---|---|
| `app/manifest.ts` | ✅ **встроено.** Мы пока держим статический `public/manifest.webmanifest` — работает, но можно упростить |
| `experimental.useOffline` | ✅ встроено в Next 16: UI, осведомлённый о сети, и повтор упавших запросов. **Кэширование не заменяет** |
| Офлайн-кэш | ❌ **не встроено.** Документация Next прямо отсылает к Serwist — поэтому выбор был не произвольным, просто для нашего объёма он избыточен |

### Прекэш и офлайн: проверено

```
установка:  shell   12 файлов  (страницы + 6 JSON контента)
после визитов: assets 15, content 1
сервер выключен → /progress/ открывается полностью
```

Что в PWA здесь действительно важно, и это уже не про фреймворк:

- **офлайн-первый запуск**: контент-пакет качается один раз и живёт в
  IndexedDB; service worker кэширует только оболочку и аудио
- **установка на домашний экран**: `display: "standalone"`, иконки 192/512,
  `theme_color` под обе темы
- **офлайн-TTS**: голос должен быть `localService: true`, см.
  `AUDIO_AND_PRONUNCIATION.md` §3
- **прогресс не кэшируется SW** — он в IndexedDB и работает без сети сам

## 1. Адаптивность: четыре размера

### 1.1. Главный тезис

Это приложение на **15 минут в день**. Основной сценарий — телефон в одной
руке, по дороге. Поэтому телефон здесь не «минимальный случай, который тоже
надо поддержать», а **основной**, а широкий экран — не «то же самое, но
шире».

Ошибка, которую легко допустить: растянуть карточку упражнения на 1400 px.
Читать строку в 1400 px невозможно, а четыре варианта ответа, разъехавшиеся
по краям экрана, невозможно сканировать глазом.

**Правило: карточка упражнения имеет предел ширины на всех экранах.
Лишнее место отдаётся не ей, а дополнительному контексту.**

### 1.2. Брейкпоинты

Tailwind 4 конфигурируется из CSS:

```css
@theme {
  --breakpoint-sm: 30rem;   /* 480px — крупный телефон          */
  --breakpoint-md: 48rem;   /* 768px — планшет / телефон лёжа    */
  --breakpoint-lg: 64rem;   /* 1024px — ноутбук                  */
  --breakpoint-xl: 90rem;   /* 1440px — большой монитор          */
}
```

| № | Размер | Устройства | Что меняется |
|---|---|---|---|
| **1** | **< 480** | iPhone SE/13/15, Android | База. Одна колонка, нижняя навигация, кнопки в зоне большого пальца |
| **2** | **480–768** | крупные телефоны, телефон лёжа, складные | Плотнее сетка вариантов, навигация всё ещё снизу |
| **3** | **768–1024** | планшет, маленький ноутбук | Навигация уезжает вбок, появляется второй столбец контекста |
| **4** | **≥ 1024** | ноутбук, монитор | Трёхзонный макет, клавиатурное управление, карточка остаётся по центру с пределом ширины |

### 1.3. Как меняется макет

```
① < 480                  ② 480–768              ③ 768–1024              ④ ≥ 1024
┌──────────────┐        ┌──────────────┐      ┌───┬────────────┐     ┌────┬──────────┬──────┐
│   прогресс   │        │   прогресс   │      │ н │  прогресс  │     │    │ прогресс │      │

│              │        │              │      │ в │            │     │ а  │          │ учим │
│   карточка   │        │   карточка   │      │ и │  карточка  │     │ в  │ карточка │ сего │
│  упражнения  │        │  упражнения  │      │ г │            │     │ и  │          │ дня  │
│              │        │              │      │ а │  max 40rem │     │ г  │ max 36rem│      │
├──────────────┤        ├──┬───┬───┬───┤      │ ц ├────────────┤     │ а  ├──────────┤ прав │
```

Ключевое: **на ④ не растягивается карточка — добавляется третья зона.** Туда
уходит то, что на телефоне прячется за тапом: формулировка правила,
разбор ошибки, список слов сегодняшнего урока.

### 1.4. Зона большого пальца — не косметика

На телефоне верх экрана недостижим для большого пальца одной рукой. Для
приложения, которым пользуются стоя в транспорте, это определяет раскладку:

```
┌─────────────────┐
│  ✗ не трогать   │  ← прогресс, счётчик — только смотреть
│                 │
│  ~ дотянуться   │  ← вопрос, текст упражнения
│                 │
│  ✓ удобно       │  ← ВАРИАНТЫ ОТВЕТА и кнопка «Проверить»
│  ✓ удобно       │
└─────────────────┘
```

Отсюда: варианты ответа **снизу**, вопрос сверху. Не наоборот, хотя визуально
«вопрос → ответы сверху вниз» кажется естественнее.

### 1.5. Три ловушки, на которых ломаются мобильные веб-приложения

**а) `100vh` на мобильных врёт.** Адресная строка то есть, то нет, и
`100vh` считается по максимальной высоте — низ экрана уезжает под браузер.

```css
/* ❌ */ .screen { height: 100vh; }
/* ✅ */ .screen { height: 100dvh; }   /* dynamic viewport height */
```

**б) Виртуальная клавиатура съедает пол-экрана.** В упражнениях с вводом
ответа это критично: поле ввода уезжает под клавиатуру.

```html
<meta name="viewport"
      content="width=device-width, initial-scale=1, viewport-fit=cover,
               interactive-widget=resizes-content">
```

`interactive-widget=resizes-content` заставляет вьюпорт сжиматься под
клавиатуру, и `100dvh` начинает означать «видимая часть». Без этого флага
нужен ручной `visualViewport`-слушатель.

**в) Вырез и индикатор Home на iOS.** В standalone-PWA контент уезжает под
них.

```css
.app {
  padding-top:    max(1rem, env(safe-area-inset-top));
  padding-bottom: max(1rem, env(safe-area-inset-bottom));
}
```

Нижняя навигация **обязана** учитывать `safe-area-inset-bottom`, иначе
кнопки окажутся под индикатором Home.

**г) Телефон лёжа — самый неудобный случай.** 400 px в высоту, а с открытой
клавиатурой ~200. Решение: на `(max-height: 30rem)` схлопывать прогресс в
одну строку и уменьшать отступы.

```css
@media (max-height: 30rem) {
  .progress-block { display: none; }
  .exercise-card  { padding-block: 0.5rem; }
}
```

### 1.6. Размеры касаний и текста

| Элемент | Минимум | Почему |
|---|---|---|
| Кнопка варианта ответа | **48 × 48 px** | рекомендация для касания; промах = засчитанная ошибка в SRS |
| Зазор между вариантами | **8 px** | меньше — промахи по соседнему |
| Польское слово в карточке | **24–32 px** | нужно разглядеть диакритику: `ż` vs `z`, `ą` vs `a` |
| Основной текст | **16 px** | меньше — Safari на iOS зумит страницу при фокусе в input |

⚠️ Последнее — реальный баг, а не предпочтение: при `font-size < 16px` в
`<input>` iOS Safari автоматически увеличивает масштаб страницы и обратно
не возвращает.

Диакритика — отдельная причина не экономить на кегле. Вся разница между
`może` и `morze`, `laska` и `łaska` — в мелких деталях знаков.

### 1.7. Клавиатура на больших экранах

На ④ (и частично ③) мышь для дрилла — это медленно. Приложение на 15 минут
должно проходиться с клавиатуры целиком:

| Клавиша | Действие |
|---|---|
| `1`…`6` | выбрать вариант |
| `Enter` | проверить / дальше |
| `Space` | проиграть звук |
| `Esc` | выйти из урока |
| `?` | показать подсказку по правилу |

Подписи к клавишам показываются только на `lg:` и выше — на телефоне они шум.

### 1.8. Темы: палитра × режим

Система перенесена из EngTutor целиком — она хорошо устроена и нет причин
придумывать заново. **Семь палитр × три режима** (светлый, тёмный, как в
системе).

Состояние живёт в двух атрибутах на `<html>`:

```html
<html data-palette="graphite" data-mode="light">
         ↑ выбирает блок       ↑ УЖЕ разрешённый режим
           в palettes.css        (не "system")
```

Ключевое решение: **«системную» тему разрешает JS**, а не `@media`. Он
слушает `matchMedia` и пишет в `data-mode` итог. Благодаря этому тёмный
набор в `tokens.css` описан ровно один раз, без дублей внутри медиазапроса.

#### Три слоя

```
theme/palettes.css   сырые цвета: --l-* (светлая) и --d-* (тёмная)
                     единственный файл с литеральными цветами
        ↓
theme/tokens.css     слой выбора: --primary: var(--l-primary)
                     и переопределение под [data-mode="dark"]
        ↓
globals.css @theme   мост в Tailwind: --color-primary: var(--primary)
                     → классы bg-primary, text-ink, border-line
```

⚠️ **`@theme inline` — обязательно.** Без `inline` Tailwind подставит
вычисленное значение переменной на этапе сборки, и смена палитры в рантайме
перестанет работать: в CSS попадёт `#ff5a5f` вместо `var(--primary)`.

#### Контракт: 23 токена

`primary`, `primary-dark`, `on-primary`, `accent-ink`, `head`, `on-head`,
`bg`, `card`, `ink`, `muted`, `line`, `soft`, `soft2`, `bar-a`, `bar-b`,
`ok`, `ok-bg`, `ok-ink`, `danger`, `danger-bg`, `danger-ink`, `warn-bg`,
`warn-ink`.

Нужны оба набора — `--l-` и `--d-`. Компоненты литеральных цветов не
содержат вообще (R6).

Отдельно стоит `accent-ink`: акцентный **текст**, не равный `primary`.
Нужен потому, что цвет заливки кнопки часто нечитаем как текст на светлом
фоне. Для карточек со словом это важно — транскрипция и активная вкладка.

#### Добавить палитру

1. скопировать блок в `palettes.css`, поменять id и значения;
2. дописать в `PALETTES` в `lib/theme/index.ts` — id, название и три цвета
   для превью;
3. всё.

#### Цвет шапки браузера

Не задаётся вручную: читается из активного токена `--head` и пишется в
`meta[name="theme-color"]`. Новая палитра получает его автоматически.

#### Никакой вспышки при загрузке

React монтируется позже первого кадра, IndexedDB вообще асинхронна.
Поэтому выбор темы живёт в `localStorage` и читается **блокирующим
инлайн-скриптом** в `<head>`:

```js
var p = localStorage.getItem('polski.palette') || 'graphite';
var m = localStorage.getItem('polski.mode') || 'system';
if (m === 'system') m = matchMedia('(prefers-color-scheme: dark)').matches ? 'dark' : 'light';
document.documentElement.dataset.palette = p;
document.documentElement.dataset.mode = m;
```

Скрипт намеренно дублирует логику из `lib/theme` — он обязан быть
инлайновым и не тянуть бандл.

### Экран «Прогресс»: шкала вместо процента

Главное решение — **показывать не абстрактный процент, а расстояние до
порога**, который решает исход экзамена. У каждой шкалы две засечки:

```
Аудирование  [слабейший]                    13% · оценка
████▏        ·         ╎      ╎
             ↑ 50% порог ↑ 65% наша цель
```

Цвет кодирует вердикт: ниже порога — красный, между порогом и целью —
нейтральный, выше цели — зелёный. Живой пример с засеянными данными:

```
Аудирование  13%  красный   ← слабейший
Чтение       13%  красный
Грамматика   60%  синий     ← выше порога, ниже цели
Письмо       35%  красный
Говорение    29%  красный
```

Это и есть иллюстрация решения D2: грамматика на 60% выглядит прилично,
но с аудированием на 13% экзамен провален. Поэтому под шкалами —
не поздравление, а объяснение:

> Проваленный модуль валит весь экзамен, поэтому время идёт слабейшему.
> Сейчас это «Аудирование».

### Пометка «оценка»

Пока контрольного среза не было, цифра — прогноз из практики, а не
измерение. Такие значения помечены словом «оценка» и опираются на
`confidence < 0.3`. Реальный балл пробника её перебивает.

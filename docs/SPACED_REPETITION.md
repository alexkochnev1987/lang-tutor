# SPACED_REPETITION.md — повторение и модель освоения

Две независимые модели памяти и то, как они складываются в занятие на
15 минут.

Реализация — `packages/engine`, 22 теста. Запуск: `pnpm --filter @polski/engine test`.

---

## 1. Почему моделей две

| Что запоминается | Модель | Где |
|---|---|---|
| Лексическая единица — узнавание | **FSRS** | `srs/scheduler.ts` |
| Лексическая единица — воспроизведение | **FSRS**, отдельная карточка | там же |
| Декларативная карточка правила | **FSRS** | там же |
| **Владение правилом как навыком** | своя mastery-модель | `mastery/mastery.ts` |

FSRS моделирует забывание **одного атомарного элемента**: у карточки есть
`stability`, и по кривой считается вероятность вспомнить именно её.

Грамматическое правило так не работает:

1. **Это навык, а не факт.** «Dopełniacz после отрицания» применяется к
   бесконечному множеству предложений. Знание формулировки ≠ умение применить
2. **Наблюдений много и они разнородны.** Правило проявляется в десятке
   типов упражнений разной сложности
3. **Подкрепляется чужой практикой.** Правило тренируется каждым
   упражнением, где оно встретилось, даже если упражнение «про другое»
4. **Есть зависимости.** Нельзя `dopełniacz` мн. ч. раньше ед. ч.; у
   лексики таких связей нет

### Одно слово — две карточки

```ts
{ kind: 'lexeme-recognition', refId: 'pl.mieszkanie' }  // pl → ru,  ~6 с
{ kind: 'lexeme-production',  refId: 'pl.mieszkanie' }  // ru → pl, ~13 с
```

У них разная сложность и свои кривые забывания. Склеивать нельзя: человек
узнаёт `mieszkanie` за месяцы до того, как сможет его воспроизвести.

## 2. FSRS: конфигурация

```ts
fsrs(generatorParameters({
  request_retention: 0.9,
  maximum_interval: 36500,
  enable_fuzz: true,          // разводит повторения, чтобы не слипались в один день
  enable_short_term: true,
  learning_steps: ['1m', '10m'],
  relearning_steps: ['10m'],
}))
```

Версия **`ts-fsrs@5.4.2`** — не v6, она в npm только в бете
(`RESEARCH.md` §7.1).

`enable_fuzz` здесь не косметика: без разброса карточки, введённые в один
день, возвращаются одной пачкой и ломают 15-минутный бюджет.

Оптимизатор параметров (`@open-spaced-repetition/binding`) в MVP не
используется — стартуем на дефолтных весах. Логи повторений пишутся с
первого дня именно для того, чтобы потом обучить `w` на реальных данных.

## 3. Главная проблема: пропущенные дни

FSRS сам по себе не знает про «15 минут». Пропустил неделю — на восьмой
день он честно выдаёт 300 просроченных карточек. Человек видит это число и
бросает. Это не теоретический риск, а основная причина отвала в SRS-приложениях.

Решение из трёх частей (`srs/queue.ts`):

### 3.1. Жёсткий потолок по бюджету

Больше, чем влезает в отведённые секунды, не показывается **никогда**.

```ts
const q = buildQueue({ scheduler, items, now, budgetSec: 240 })
q.estimatedSec  // ≤ 240 всегда
q.deferred      // сколько не влезло — просто остаётся просроченным
```

Тест: 200 просроченных карточек при бюджете 180 с → в очередь попадает
не больше 30.

### 3.2. Сортировка по срочности, а не по дате

Это неочевидно и важно. Первым идёт не то, что просрочено дольше всех, а
то, что **вот-вот забудется**:

```ts
scored.sort((a, b) => a.retrievability - b.retrievability)
```

Карточка, просроченная на месяц, но лёгкая, менее срочна, чем вчерашняя,
но трудная. Сортировка по дате тратила бы бюджет на то, что и так ещё
помнится.

### 3.3. Режим разгребания

Если просрочки больше, чем на **три дня бюджета** — завал:

```ts
q.backlog === true
q.suppressNewItems === true   // новые слова и правила сегодня не вводятся
```

Логика: добавлять новое в переполненную очередь — значит углублять яму.
Сначала разгрести, потом продолжать. Генератор занятия это уважает и
пишет пользователю honest-сообщение, а не делает вид, что всё по плану.

### 3.4. Урезание ввода новых слов

Даже без завала новое слово — это не 20 секунд сегодня, а хвост повторений
на недели вперёд:

```ts
newItemAllowance(planned, queue, budgetSec)
// отдаёт под новое не больше половины свободного остатка
```

Тест: 25 просроченных при бюджете 180 с → из 10 запланированных слов
вводится меньше.

## 4. Mastery-модель для грамматики

```ts
interface RuleMastery {
  grammarRuleId: string
  mastery: number        // 0..1
  attempts: number
  correct: number
  lastPracticedAt: number | null
}
```

### 4.1. Обновление

Скользящая оценка с двумя поправками:

```ts
weight    = alpha × (0.5 + exerciseDifficulty / 10)
effective = correct ? weight : weight × 1.5
mastery   = base + (target − base) × min(1, effective)
```

**Поправка на сложность.** Верный ответ на упражнение сложности 5
информативнее, чем верный выбор из двух вариантов.

**Асимметрия.** Ошибка штрафует в 1,5 раза сильнее, чем успех
вознаграждает. В грамматике одна систематическая ошибка перевешивает
несколько случайных попаданий: угадать можно, систематически ошибаться —
нет.

### 4.2. Затухание

```ts
mastery × (1 − 0.15) ^ (дней / 30)
```

За месяц без практики навык теряет 15%. **Медленнее, чем забывается
слово** — и это не произвол: правило подкрепляется любым упражнением, где
оно встретилось, а слово — только своим отзывом.

Тест фиксирует это: `mastery 0.9` через 30 дней остаётся выше 0.7.

### 4.3. Пороги

```
mastery < 0.60  →  слабое, получает дриллы
mastery ≥ 0.85  →  освоенное
```

`weakestRules()` возвращает слабейшие с учётом затухания — давно не
практикованное всплывает само, без отдельного планировщика.

## 5. Сборка занятия

`lesson/generator.ts`. Приоритеты по убыванию:

| # | Активность | Почему здесь |
|---|---|---|
| 1 | **Повторения** | Иначе теряется уже вложенное время |
| 2 | **Новая грамматика** | По программе — но не при завале |
| 3 | **Дриллы по слабым правилам** | Вытесняют правило дня из блока практики |
| 4 | **Новые слова** | Только сколько реально потянем |
| 5 | **Экзаменационный блок** | Слабейшему модулю |
| 6 | **Разбор ошибок** | Всегда в конце, фиксированной длины |

### Слабейший модуль перебивает программу

Это прямое следствие помодульного порога 50% (`PLAN.md` D2):

```ts
const moduleId = verdict.weakest && verdict.gap > 0
  ? verdict.weakest        // ← аудирование, если оно проседает
  : plan.examFocus         // ← иначе ротация из программы
```

Тест: план дня говорит `reading`, но аудирование на 30% — блок уходит
аудированию.

### Занятие объясняет себя

У каждой активности есть `reason`, у занятия — `notes`:

```
«Отложено 47 повторений — не поместились в бюджет»
«Завал очереди: новые слова сегодня не вводятся, разгребаем старое»
«Новых слов урезано: 7 → 3, нагрузка высокая»
«слабейший модуль, отставание 35 п.п.»
```

Пользователь должен видеть, **почему** сегодня не по плану. Молча урезать
программу — верный способ потерять доверие к ней.

## 6. Готовность к экзамену

`readiness/readiness.ts`. Правило сдачи — **стратегия в данных**, не число:

```ts
type PassRule =
  | { kind: 'per-module-floor'; thresholdPercent: number }   // польский B1
  | { kind: 'aggregate'; thresholdPercent: number }          // польский A1/A2
  | { kind: 'weighted-average'; weights; threshold: number }
```

Тест, показывающий, зачем это нужно, — один и тот же набор баллов:

```
listening 40 · reading 95 · grammar 95 · writing 95 · speaking 95

per-module-floor → НЕ ГОТОВ   (аудирование валит всё)
aggregate        → готов      (среднее 84%)
```

Запас над официальным порогом — **15 п.п.** (`SAFETY_MARGIN_PP`): реальный
экзамен тяжелее тренировки. При пороге 50% цель приложения — 65%.

## 7. Что не реализовано

| | Почему |
|---|---|
| Оптимизация весов FSRS на логах | Нужны накопленные `reviewLogs`. Логи пишутся с первого дня |
| Учёт времени суток и усталости | Нет данных, чтобы это калибровать |
| Прогноз `moduleReadiness` из упражнений | Сейчас обновляется только на контрольных срезах. Промежуточная оценка по ходу — следующий шаг |
| Межъязыковая интерференция в FSRS | `interferenceRu` влияет на подбор дриллов, но не на интервалы. Возможно, ложные друзья стоит планировать агрессивнее |
